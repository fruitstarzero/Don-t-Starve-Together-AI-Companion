# 星露谷与饥荒实现复盘

## 两个项目的技术选择

| 项目 | 星露谷 0.4.2 | 饥荒联机版 0.5.0 |
| --- | --- | --- |
| 当时核对版本 | 游戏1.6.15.24356、SMAPI4.5.2 | 游戏756039 |
| 基础 | 基于 StardewValley-MCP 进行本地适配 | 自制 Lua 服务端模组与本机 Node 桥接 |
| 同伴 | NPC＋影子农夫；外观借用资源，身份独立 | 原版温蒂实体、原版状态机，显示名AI伙伴 |

| 远程入口 | F10/屏幕按钮，游戏对话及QQ指令 | F10/屏幕按钮，游戏聊天、呼叫/传送与模式按钮 |

## 实际制作顺序

### A. 先建立角色与模型基础

QQ项目提供既有人设、模型调用定位、近期对话、重要记忆和自愿日记。新游戏在其上增加游戏规则，不把某一款游戏的专用工具提示带到另一款游戏。游戏与QQ的回复按来源路由，游戏聊天不自动重复发送到QQ。

历史原型曾通过QQ代码中的 `findCodex` 找到CLI；当前独立分享版 `bridge/model.mjs` 从安装者配置的路径或PATH找到CLI，用结构化Schema获得只读规划；关闭该规划进程的shell、插件、多代理、内置记忆、图像工具和联网搜索。它输出计划，真正动作由游戏适配器执行。这是原型到独立版的实现记录，不是对未来CLI参数兼容性或订阅额度的保证。以后换接口时先核对当时产品文档与实际安装版本。

角色人设和共享记忆都通过本机读取后交给模型。私人记忆共享曾需要明确授权；迁移时保存共享范围说明，不把账号凭据或私人内容放入开发资料。程序未设置每日100次硬上限，仍可能受到账号模型额度和服务故障影响。

### B. 星露谷先做自主基础，再补体验

先接入真实季节、天气、作物、金币、体力和背包，再实现走动、取种、播种、浇水和按需购买种子。种子优先普通箱，缺种才按真实商店库存、成熟天数与剩余季节选择；保留2000金币是当时用户选择的游戏策略，不应硬写到所有游戏。

随后加入游戏内对话、远程呼叫、跟随协助与读取主人速度。实跑发现取种前反复回耕地的顺序错误，改成先取适量种子再走去空地。这说明动作单独可用，还需要检查整条流程中的阶段顺序。

钓鱼使用真实地点鱼表结算而不弹主人小游戏；鱼大小、完美奖励与NPC接触伤害并未完全复刻。以后选择“越像真实玩家越好”时，应尽早确定实体架构，不能在NPC方案完成后只靠提示词补成完整玩家。

## 重要故障和修复方法

### 饥荒当前的请求与执行链

1. 游戏管理组件约每2游戏秒轮询一次，把主人/世界/分片/会话、模式版本、属性、背包、附近对象、事件和消息交给本机桥接；本地人物Tick约0.25游戏秒一次，不依赖每帧模型推理。
2. Node优先处理当前聊天；在允许的自主模式或社交候选下再触发规划。正常规划间隔起点45秒，失败按指数退避，最大间隔300秒；模型全局串行，避免多会话同时挤占同一生成入口。这些是当前实现参数，不是建议所有游戏采用相同频率。
3. 模型输入包含当前快照、任务、最近游戏问答、重要记忆、长期项目、经验、配方和知识；经授权开关决定是否加QQ共享记忆。0.8.0已将稳定人设、游戏知识与执行记忆分开；独立分享版只读自己的role.md和游戏目录，不读取QQ项目。
4. 独立短生命周期Codex进程读入JSON，受输出Schema与工具限制；当前模型超时165秒。解析时必须有真实完成事件，错误/失败或出现执行命令、改文件、MCP工具调用都视为无效；不能只从输出里找到一段像JSON的文字就宣布成功。
5. Node复核身份/模式版本与响应时效，Lua再校验命令、流程、当前手动模式和任务守卫。被接受的模型结果只代表安排生效；实际执行仍检查真实材料、距离、状态与容量。
6. 原生动作成功、建造事件、入库数量、真实到达等更新任务账本；下一轮快照镜像回后台。模型的 `taskStatus=complete/none` 不清理游戏任务。

游戏时钟与真实时钟不同：动作Tick、发言冷却、阻塞与重试主要按游戏时钟，模型调度和超时用Node真实时钟。暂停世界时应单独检查这两套时间的影响。

### 当前数值是实现参数，不是跨游戏规则

| 项目 | 当前饥荒实现 |
| --- | --- |
| 有限流程 | 最多6步；完成证据逐步保存 |
| 任务终态历史 | 最近8项 |
| 有限任务无实质进展 | 120游戏秒后阻塞，等待30游戏秒再核对 |
| 制作普通缺料搜索 | 仅适配的常见材料、白天，最多4个点、每点18游戏秒；不是全图搜索 |
| 主动发言 | 普通至少90游戏秒、紧急至少30秒；同话题至少300秒，闲聊机会约240秒 |
| 发言回看 | 最近20条，列表默认3条，长文可展开分页；气泡8秒 |

这些参数在新游戏中应结合时间流速、玩法节奏和性能重新选择。尤其不能把饥荒的珍贵物品数量阈值或星露谷的2000金币保留当作共同角色的永久偏好。

### 出错表现与处理

| 表现 | 实际原因/证据 | 修复与下次的检查点 |
| --- | --- | --- |
| 进世界崩溃 | 两个Show Me版本对同一玩家实体注册同名网络变量，原生断言 | 真实日志＋单版/双版回调对照；备份配置后停用重复版本，不随意改Workshop源码 |
| 进世界后RPC报错 | 模组受限全局没有直接 `pcall` | 使用 `GLOBAL` 中的函数，回归覆盖完整客户端回调 |
| 输入文字模糊/黑 | 控件进入编辑态后重设颜色 | 同时设编辑/非编辑文字与光标；在真实控件路径核对 |
| 气泡消失太快 | 瞬时气泡不适合长回复 | 采用8秒显示及最近发言小窗，保留情境、展开和分页 |
| 能做木板却造不出箱 | 建筑需要原版 `BufferBuild` 后放置 | 复用真实builder方法，检查材料只扣一次、建筑实际落地 |
| 在错误科技站来回走 | 把science标签当作满足科技 | 记录并匹配实际科技树；未知旧记录不当作有效匹配 |
| 工具取出后又回原箱 | `GiveItem` 使用 `prevcontainer/prevslot` 返回提示 | 有意转移前清理返回提示，回执核对实际所在容器 |
| 满仓造箱却无格子取料 | 扩容依赖原料，背包和箱子同时满形成闭环 | 白天安全基地有界临时放普通货物，记录并拾回；不丢生存/珍贵/未知物品 |
| 满包无法继续加工 | 只检查“包满”，忽略真实扣料腾格/成品叠堆 | 使用原版实际选料和容量检查 |
| 菜地取消后又自动出现 | 自动发现覆盖用户取消 | 保存取消区域，明确重新安排才恢复 |
| 大批采集存一趟后从零算 | 只看随身库存 | 本轮真正入库才累计 `delivered`，保存和重规划不清零 |
| 问攻略就停工 | 聊天/模型回答和行动切换混在一起 | 普通聊天只更新对话；明确计划才切换本地行动 |
| 临时跟随后忘记旧任务 | 单个当前任务被手动命令清空 | 任务账本保存目标、阶段、进度；暂停与取消分开 |
| 模型说complete就跳过动作 | 把语言判断当本地完成证据 | 每步由真实数量、事件、到达或物资状态确认 |
| 完成后迟到计划又启动旧活 | 同一revision内任务已经终结 | 增加任务ID/阶段/终态守卫，不能只检查模式版本 |
| 保护任务后自主做饭永远不换事 | 主人任务与自主持续活动一律锁定 | 主人/有限任务保护，自主持续活动可按新需求调整 |
| 收到错误消息却被算模型通过 | 验证只检查有无reply | 错误显式 `modelError`，验收排除错误提示 |

## 资源、长期项目与模组的处理

箱子索引记录已观察的同类物品位置，区分当前核对库存与离开后的旧记录；实际取物前重新检查。拆堆按缺额，普通情况留样品；生存紧急例外与制作/进锅保护分开。存货留自己的食物、照明、工具、装备与当前配方材料，不能为了任务把生存用品全放掉。

长期菜地/移植区单独保存位置和取消记录，空闲时回访；手动跟随或待命优先。一次“收完放箱子”不自动变永久习惯，是否值得记经验由实际重复需求、上下文和结果判断。

对原版标准容器或配方钩子，可沿用模组改变后的容量、装备槽、食谱；纯显示和专属GUI要明确边界。木牌传送GUI没有直接适配，按玩家需求另做主人发起的地表传送集合，不能称作已经掌握木牌模组。

## 验收结论怎么读

- 星露谷 `verification.json` 记录跟随浇水与快走已确认，部分旧说明仍写“待实测”；本归档采用较新的结构化记录及会话中的用户确认。
- 饥荒0.4.0较早完整原生运行56/60，后续基地专项19/19；分批合并用于覆盖追踪，不能称“最终单轮60/60”。
- 饥荒0.5.0是58/58本地自动回归、26个Lua文件语法、135个UI API调用检查通过。没有为该版本启动客户端或专服，没有新模型探测。
- 玩家之前确认过的UI与传送，不自动证明后来新增的多步任务在真实世界已通过。下次仍按当前测试清单验收。
